## Difetti osservati, oracoli e correzioni

Il percorso Back iniziale torna da Settings a Dashboard invece di chiudere il drawer. La patch `cc426b1` usa `key(entry.id, drawer.isOpen)` per ricreare **soltanto il callback Back**, senza ricreare le entry di navigazione; il caso isolato e il successivo gruppo debug passano. Questi esiti non dimostrano una causa precisa nel ritardo della prima registrazione del callback o in `SnapshotStateObserver`.

Il confronto precedente al fix More è **evidenza differenziale invalida**: la stessa fixture bridge `47a78d9` fallisce con `clickNativeMoreButton timeout` sulla versione precedente e su quella successiva. La [disposizione del campione](../artifacts/navigation-form-ui/ccbc0f13-84e8-4a91-b77c-18caa37a7705/bridge-fixture-disposition.json) conserva `not_differential_evidence`; il [risultato sulla versione precedente](../artifacts/navigation-form-ui/ccbc0f13-84e8-4a91-b77c-18caa37a7705/more-before-fix-result.json) da solo non dimostra la correzione. La disposizione registra anche un caso TCG isolato passato in 14,612 s sul medesimo APK test, senza attribuire una causa a `SnapshotStateObserver`.

Nel run `5e0d7e2a`, il [diagnostico `43fa3866`](../artifacts/navigation-form-ui/5e0d7e2a-df7c-46f4-a902-ebd02a4403a7/diagnostic-report.json) mostra More come etichetta `TextView` sotto un `View` cliccabile con due figli. Imporre a quel controllo la classe legacy `Button` è un oracolo invalido: Compose 1.8.x assegna tale classe nei casi `isFake` o senza figli. Il driver `8202f45` usa il primo controllo cliccabile, lo stato checkable/checked e `ACTION_CLICK`, senza fallback a tap. I due run successivi verificano More, senza cambiare i byte della produzione.

Per A, i diagnostici [prima del tocco](../artifacts/navigation-form-ui/cf92fb2e-a100-49a9-8bbf-99232efea39f/diagnostic-report.json) (`2f605b3f`) e [dopo il tocco](../artifacts/navigation-form-ui/cf92fb2e-a100-49a9-8bbf-99232efea39f/diagnostic-2-report.json) (`823d411b`), insieme all'[evento manuale](../artifacts/navigation-form-ui/cf92fb2e-a100-49a9-8bbf-99232efea39f/manual-dashboard-touch.json), confermano il root dell'app target e Settings/Profile ancora visibili. Dashboard è presente nella navigazione, ma il suo contenuto non compare. È una diagnosi del fallimento, non una nuova qualifica.

La correzione produzione `d2bef51` imposta `restoreState = target != "dashboard"`: il ritorno a Dashboard non ripristina una destinazione precedente. Il commit `3ae685f` aggiunge la regressione `NavigationPermissionBoundaryTest#nonAdminCanReturnFromSettingsAccountToDashboardTwiceWithoutRestoringTheChildRoute`, portando il gruppo a tredici casi. Il [confronto Dashboard](../artifacts/navigation-form-ui/751298f0-85af-489a-978b-acf127e61ff9/dashboard-regression-input.json) usa **lo stesso test APK `b1887b…`**: sull'app precedente `ceec4d…`, sorgente `cc426b1`, [fallisce in 57,208 s](../artifacts/navigation-form-ui/751298f0-85af-489a-978b-acf127e61ff9/dashboard-regression-before-result.json), nella verifica del titolo Dashboard alla riga 167; sull'app corretta `c4f89d…`, sorgente `3ae685f`, [passa in 16,383 s](../artifacts/navigation-form-ui/751298f0-85af-489a-978b-acf127e61ff9/dashboard-regression-after-result.json). I log prima/dopo sono conservati nello stesso run. Questa prova differenziale è distinta dal confronto bridge More invalido.

Il successivo run `751298f0` fallisce dopo tredici checkpoint: il generico errore host e il report `DASHBOARD_NAVIGATION_MISSING` non dimostrano la causa del ritardo o un problema di worker thread. Il driver finale `8efe24f` riporta il target in primo piano e attende `bottomReady` prima della verifica d'identità conclusiva; il coordinatore host attende fino a 180 s. Il run fresco completo verifica il profilo corretto e il cleanup; il suo PASS non attribuisce retroattivamente una causa certa al fallimento precedente.

## Criterio qualificato localmente e limiti

Il controllo di cache/revoca TCG è rappresentativo; non prova ogni cache di ogni modulo.

Il percorso firmato conclude **19 destinazioni Admin, 18 A, 17 B** nei [tre report di navigazione](../artifacts/navigation-form-ui/179e6e49-c86a-4bd2-a045-942781d7dd06/nav1-routes-report.json), [A](../artifacts/navigation-form-ui/179e6e49-c86a-4bd2-a045-942781d7dd06/nav2-routes-report.json) e [B](../artifacts/navigation-form-ui/179e6e49-c86a-4bd2-a045-942781d7dd06/nav3-routes-report.json). Il [report ruolo](../artifacts/navigation-form-ui/179e6e49-c86a-4bd2-a045-942781d7dd06/nav3-role-report.json) verifica cinque fasi, rimozione di route/drawer dopo revoca, visibilità dopo ripristino e identità conservata. Il ledger conclude **15 checkpoint server ordinati**, vincolando quattro UUID di sessione distinti: Admin nativo, A nativo, B nativo e Admin host. Il client host tiene i token soltanto in RAM. I checkpoint, i dieci metodi nativi e i gruppi JUnit restano unità distinte.

Le osservazioni server confrontano i tre QA fissi, le proiezioni selezionate di identità/profili e le mappe complete dei permessi; non certificano ogni colonna `updated_at` o tutti gli utenti del servizio. La lista utenti Admin resta in RAM e non viene catturata o persistita. Il client host non equivale a un secondo telefono. I gruppi debug non provano tutte le funzioni del release R8 e le diagnosi manuali non aggiungono route superate.

Il PASS locale chiude soltanto il criterio V02 nel perimetro descritto. Restano esclusi CI, pubblicazione e una dichiarazione di parità globale. Le evidenze qui collegate non contengono password, token, JWT o owner revision.
