# Piano proposto: cardtrader-proxy, autorizzazione distinta

Nessun deployment o canary eseguito. Il servizio è condiviso da web e Android. Questo piano non autorizza update-tcg-prices, update-prices, cron, scritture di carte o modifiche ai segreti.

Inviare soltanto `backend-proposals/cardtrader-proxy/index.ts` e `quote-contract.ts`, dopo controllo degli hash di `verification.json`. Il backup originale resta in `artifacts/s02-proxy-preparation/deployed-backup/`; non modificare né distribuire le copie di staging o i file native-v12. Il pacchetto cron `backend-proposals/update-tcg-prices` richiede una seconda autorizzazione esplicita.

1. **Fissare la preimmagine.** Dopo autorizzazione dell'utente, creare una nuova directory esclusiva del run. GET Management solo metadati e corpo di cardtrader-proxy: richiedere ID `23c851ba-f056-4fe2-a04d-52a8536a266a`, nome/slug corretti, ACTIVE, versione 17, verify_jwt false e corpo SHA `abe60a7cef81679b9b4aee5734a66dee784e4e2a65b2f7be4a699de4bb4dbb65`. Se differisce, fermarsi e rivedere il nuovo codice. Salvare metadata completi, ESZIP, hash e parametri import map effettivi. La preimmagine attuale non ha import map. Management token solo RAM, redirect vietati, nessun segreto in argv/log.
2. **Un solo invio.** Verificare gli hash dei due file in verification.json e rileggere immediatamente versione/corpo. Con un solo operatore, POST `/v1/projects/crqnfbahytzenisospcx/functions/deploy?slug=cardtrader-proxy` con due file multipart, index.ts e quote-contract.ts, metadata `{"entrypoint_path":"index.ts","name":"cardtrader-proxy","verify_jwt":false}`. Prenotare durevolmente l'invio con hash e preimmagine prima del POST. Nessun retry, bundleOnly, aggiornamento chiavi o altro slug. Rimane una finestra di concorrenza perché Management non fornisce CAS di versione sul deployment.
3. **Riconciliare e campionare.** Rileggere metadata/corpo, richiedere stesso ID/slug, ACTIVE, versione successiva e i due moduli attesi. Un esito di trasporto incerto richiede osservazione, mai ripetizione automatica del POST. Soltanto se autorizzato insieme al deployment: JWT di QA riservato, GET ricerca e GET prezzi di un blueprint restituito dalla ricerca; verificare v2/EUR/minorUnit2/id/cents interi oppure errore/null esplicito. Provare anche rifiuto senza JWT. Nessuna chiamata cron, nessuna scrittura tgc_cards e nessuna lista di clienti. Chiudere localmente soltanto la sessione QA creata per il campione. Un esito positivo proxy non qualifica il vecchio cron o i prezzi già salvati.
4. **Integrare il parser successivamente.** Solo dopo conferma proxy v2, applicare il pacchetto Android V12 e qualificare JVM/Android con build coordinata. I sorgenti qui predisposti non sono inclusi nell'APK attivo. I client web precedenti conservano le tre chiavi di risposta e ricevono soltanto centesimi EUR validati. La ricerca mantiene il contratto array esistente; il controllo JWT applicativo resta attivo.
5. **Rollback revisionabile.** Nessun rollback automatico. Prima di un rollback autorizzato, richiedere versione/corpo corrispondenti al solo deployment di questo run, per non sovrascrivere interventi successivi. PATCH `/v1/projects/crqnfbahytzenisospcx/functions/cardtrader-proxy`, corpo ESZIP originale, Content-Type application/vnd.denoland.eszip, verify_jwt=false ed entrypoint_path originale nei parametri, preservando gli eventuali parametri import map effettivi. Poi rileggere corpo/metadata. Un rollback crea una nuova versione; non promette il ripristino del numero 17. La nuova app rifiuterebbe il contratto legacy senza unità; non disabilitare la guardia per nascondere l'incompatibilità. Questo proxy non scrive prezzi sul DB, quindi non esiste rollback di dati da automatizzare.

La forma Management proposta segue il piano già revisionato per update-prices; prima dell'invio operativo va verificata sul contratto API corrente. Le azioni globali restano subordinate all'autorizzazione separata dell'utente e alla preimmagine corrispondente.
